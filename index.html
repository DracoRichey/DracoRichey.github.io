03 — Enhancements

Artifact Enhancements

ENHANCEMENT 01

Software Design and Engineering — bcrypt Authentication

Security

The original application stored and compared passwords in plaintext with no hashing or salting. This enhancement replaced that system with bcrypt password hashing via a Mongoose pre-save hook and introduced JWT-based middleware to protect write routes across the API.

▶ Read Full Narrative

Artifact Description

Travlr Getaways is a full-stack travel booking web application built on the MEAN stack: MongoDB, Express.js, Angular, and Node.js. Developed approximately six months ago in CS-465. The application has two frontends — a server-rendered customer-facing site built with Express and Handlebars, and an Angular SPA for admin management — backed by a REST API secured with JWT authentication.

Why This Artifact

I selected Travlr Getaways for this enhancement because it contained a real, demonstrable security flaw: passwords were stored and compared in plaintext. There was no hashing, no salting, and no meaningful protection for user credentials. This made it an ideal candidate for a security-focused enhancement because the problem was concrete, the fix was non-trivial, and the before-and-after contrast is clear.

The Enhancement

The core change was integrating bcrypt into the User model using Mongoose's pre-save hook. When a user document is saved and the password field has been modified, the hook fires before the write completes and replaces the plaintext password with a bcrypt hash at a cost factor of 10. A companion instance method, comparePassword, handles login verification by running bcrypt.compare against the stored hash.

One design decision worth explaining is how async bcrypt operations are handled within the Express route structure. Both the pre-save hook and comparePassword are async functions. The hook uses async/await and calls next() only after hashing completes, which ensures Mongoose never writes a plaintext password even if the save is triggered concurrently. The login controller is also fully async, awaiting both the database lookup and the password comparison before issuing a token.

The JWT middleware extracts the Bearer token from the Authorization header, verifies it against the JWT_SECRET environment variable, and attaches the decoded payload to req.user. All write routes — POST, PUT, DELETE — are protected behind this middleware. Read routes remain public.

One item from the original plan was descoped: a user registration endpoint. Given time constraints and the scope of the other two enhancements, registration was not implemented. User accounts are currently managed directly in the database.

Reflection

The most valuable thing I learned was how authentication middleware composes in Express. The biggest challenge was understanding the async flow inside the Mongoose pre-save hook — specifically that calling next() before the await resolves would write the plaintext password.

This enhancement partially meets Course Outcome 5 (security mindset, mitigating design flaws, ensuring data privacy) and Course Outcome 4 (use of industry-standard tools and techniques).

ENHANCEMENT 02

Algorithms and Data Structures — Search, Filter, and Sort

Query Design

The original trip listing was a single Trip.find().exec() call that returned all records in insertion order with no filtering or sorting. This enhancement replaced it with a dynamic query API accepting search terms, date ranges, sort field, and sort order.

▶ Read Full Narrative

The Enhancement

The enhanced tripsList function accepts optional query parameters: search, sortBy, order, before, and after. These dynamically construct a MongoDB filter object and sort object before the query executes.

The search parameter builds a case-insensitive regular expression applied as an $or condition across destination and description fields. The before and after parameters filter by departureDate using $lte and $gte operators. Both can be applied simultaneously using the spread operator pattern to construct a date range without overwriting either bound.

Indexes were added on destination and departureDate to ensure MongoDB resolves filtered queries without full collection scans.

Pseudocode

FUNCTION tripsList(req, res):
  EXTRACT search, sortBy, order, before, after FROM req.query

  SET filter = {}

  IF search EXISTS:
    SET filter.$or = [destination matches search,
                      description matches search]

  IF before EXISTS:
    SET filter.departureDate.$lte = before

  IF after EXISTS:
    SET filter.departureDate.$gte = after

  SET sortField = sortBy OR 'departureDate'
  SET sortOrder = IF order == 'desc' THEN -1 ELSE 1

  QUERY Trip.find(filter).sort(sortField, sortOrder)
  RETURN results as JSON

Reflection

The main design decision was where to put the filtering logic — in the database query or in application code after fetching all records. Filtering in the query is clearly correct: it reduces data transferred, uses indexes, and scales with the dataset.

This enhancement meets Course Outcome 3 (designing computing solutions using algorithmic principles, managing trade-offs).

ENHANCEMENT 03

Databases — Mongoose Migration and Aggregation Pipeline

Database

Trip data was originally read from a static JSON file on disk. The Mongoose Trip model existed but was completely disconnected from the application routes. This enhancement replaced all JSON file reads with live Mongoose queries and added an aggregation pipeline for destination analytics.

▶ Read Full Narrative

The Enhancement

Every controller function that previously called fs.readFileSync now queries the Trip model directly using Trip.find(), Trip.findById(), Trip.findByIdAndUpdate(), and Trip.findByIdAndDelete(). The Mongoose connection is established in db.js on startup with event listeners for connected, error, and disconnected states.

The most significant addition is an aggregation pipeline at GET /api/trips/report. It filters to future trips, casts the price String to a number using $toDouble, groups by destination calculating trip count and price statistics, and sorts by trip count descending.

The $addFields cast is worth explaining. Ideally price would be stored as a Number from the start. Migrating existing documents was out of scope, so casting at query time is a practical trade-off that produces correct numeric aggregations without a data migration.

Pseudocode

PIPELINE tripsReport:

  STAGE 1 - $match:
    WHERE departureDate >= today

  STAGE 2 - $addFields:
    SET priceNum = $toDouble(price)

  STAGE 3 - $group:
    GROUP BY destination
    CALCULATE tripCount = $sum(1)
    CALCULATE avgPrice  = $avg(priceNum)
    CALCULATE minPrice  = $min(priceNum)
    CALCULATE maxPrice  = $max(priceNum)

  STAGE 4 - $sort:
    ORDER BY tripCount DESCENDING

  RETURN array of grouped destination summaries

Reflection

The most important thing I learned is how much architectural debt can hide in a codebase that appears functional. The app rendered trips because the JSON file existed — but replacing it with a live database connection makes the application honest about what it actually is.

This enhancement meets Course Outcome 4 (well-founded techniques delivering industry-specific value) and partially meets Course Outcome 3 (design trade-offs in schema design).
